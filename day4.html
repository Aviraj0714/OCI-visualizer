🔨 Traditional Infrastructure vs. IaC

⏱ 25 minFoundationalExam Weight: Medium
Learning Objectives
  • List the failure modes of manual, console-driven provisioning at scale.
  • Explain configuration drift and why it compounds over time.
  • Watch the same environment built manually vs. via IaC and compare the outcome.
Prerequisite: none — this is lesson one
👷
Real-World Analogy

Manual provisioning is like building furniture from memory, slightly differently each time — the tenth bookshelf never quite matches the first. Infrastructure as Code is a CNC machine cutting from the same digital blueprint every time: identical, fast, and reproducible on demand.

🏢
Business Use Case

A retail company's ops team spends three days manually clicking through the OCI Console to stand up each new regional store's environment — VCN, subnets, compute, NSGs. By month six, no two regions are configured identically, and nobody can say why region 4's checkout latency is different from region 1's, because nobody documented what was actually clicked.

Manual provisioning fails in five predictable ways as an organization scales: configuration drift (environments silently diverge from each other over time), human error (a missed checkbox during a 40-step console wizard), slow deployment (hours or days instead of minutes), inconsistent environments (dev, test, and prod are never quite the same), and downtime risk from untested, undocumented manual changes.

🎯
Exam Tip

When a question describes environments that have "silently diverged" or "no longer match," the term being tested is configuration drift — you'll see this again in Module 5.

⚠
Common Trap

IaC doesn't eliminate human error — it eliminates inconsistent human error. A bad Terraform config still deploys badly, but it deploys the same way every time, and it's reviewable before it runs.

Interview & Scenario Questions ▼

Q: Your team says "we already have shell scripts that provision our servers, isn't that Infrastructure as Code?"

→ Partially. Scripts are code, but most ad hoc scripts are imperative and non-idempotent (re-running them can cause errors or duplicate resources). True IaC tools like Terraform track state and compute an idempotent plan, so re-running is always safe.

⚖ Declarative vs. Imperative

⏱ 25 minFoundationalExam Weight: High
Learning Objectives
  • Distinguish declarative ("what") from imperative ("how") tooling.
  • Match a real task to the right tool: Terraform, Ansible, Shell, Python, or PowerShell.
Prerequisite: Benefits of IaC
🍽
Real-World Analogy

Declarative is telling a taxi driver an address — you don't care about the route, you just want to arrive. Imperative is giving turn-by-turn directions yourself. Terraform is the address; a shell script is the turn-by-turn directions.

Simulator › Tool Recommendation Engine

Select the task you need to accomplish:

Provision a VCN + subnets + compute across 3 environments
Restart a hung service on 50 running servers right now
Install packages & configure an app on existing servers
Run a one-time data migration script
Configure a fleet of Windows Servers

📋 Declarative (Terraform)

You describe the desired end state. The engine figures out the steps, in the right order, and is naturally idempotent — running it twice produces the same result.

🛠 Imperative (Ansible / Shell / Python / PowerShell)

You specify the exact sequence of steps to execute. Powerful for one-off actions and configuration management, but you own correct ordering and re-run safety yourself.

🎯
Exam Tip

Ansible is often described as "imperative with declarative elements" — playbooks execute tasks in written order (imperative) but many modules are individually idempotent. Terraform is purely declarative and state-driven.

⚠
Common Trap

Terraform provisioners (local-exec, remote-exec) let you run imperative shell commands from within a declarative Terraform config — but Oracle's own documentation calls this a last resort, not the primary model.

🎯
Exam Tip
count and for_each both create multiple resource instances, but for_each keys instances by a stable map/set key, so reordering the input list doesn't force unrelated resources to be destroyed and recreated the way count's index-based addressing can.

  
⚠
Common Trap
HCL is whitespace-insensitive but quote-sensitive: block type and name labels must be quoted strings, and bare words are interpreted as references, not literals — a classic syntax error source.

💾 terraform.tfstate

  
⏱ 30 minCore ConceptExam Weight: Very High

  
Learning Objectives
    
    
  • Explain what state maps and why Terraform can't function without it.
    • 
    
  • Identify sensitive information that commonly ends up in state.
    • 
    
  • Watch the state file update live as a resource is added.
    • 
  

  
Prerequisite: Module 2 complete


  
📜
Real-World Analogy
State is Terraform's inventory ledger. Without it, Terraform would have no way to know that "the VCN in your config" and "OCID ocid1.vcn.oc1..xyz already running in OCI" are the same object — it would try to create a duplicate every time.


  
terraform.tfstate is a JSON file mapping every resource in your configuration to its real-world OCID, tracking metadata, dependency ordering, and often sensitive values (like generated passwords) in plain text — which is exactly why state must be protected like a secret.

Common Trap
Never hand-edit terraform.tfstate directly. Use terraform state mv, terraform state rm, or terraform import — manual edits routinely corrupt the JSON structure or desync it from reality.

  
🎯
Exam Tip
State stores the dependency graph too, not just resource IDs — this is what lets terraform destroy tear things down in the correct reverse order.

☁ Remote Backends

  
⏱ 20 minCore ConceptExam Weight: High

  
Learning Objectives
  • Compare local state, OCI Object Storage, and Terraform Cloud as backends.

  
Prerequisite: State Locking


  

    
💻 Local State
Fastest to start. No locking, no team visibility, single point of failure (one laptop).

    
📦 OCI Object Storage
Encrypted, versioned, shared. Supports locking with the right configuration. OCI-native choice.

    
☁ Terraform Cloud
Fully managed: state, locking, run history, policy-as-code, and a UI — multi-cloud by design.

  


  
⚡
60-Second Revision
Local state is fine for solo learning; any team, anywhere, needs a remote backend for locking and shared visibility — this is one of the most repeated best practices in Module 6.

🐶 Drift Detection

  
⏱ 25 minCore ConceptExam Weight: Very High

  
Learning Objectives
    
    
  • Trigger drift by simulating a manual OCI Console change.
    • 
    
  • Read a drift report and identify what changed outside Terraform.
    • 
  

  
Prerequisite: Module 4 complete


  
🐶
Real-World Analogy
Drift is what happens when someone rearranges the furniture without updating the floor plan. The floor plan (your Terraform config) still says the couch is against the wall — but it isn't anymore.

🎯

Drift Detection in Resource Manager is read-only by design — it reports differences, it never auto-corrects them. Correcting drift is always a deliberate follow-up action (see Reconciliation, next lesson).

🖥 Remote Execution (Provisioners)

  
⏱ 20 minCore ConceptExam Weight: Medium

  
Learning Objectives
  • Differentiate remote-exec from local-exec.
  • Explain why Oracle recommends provisioners as a last resort.

  
Prerequisite: Templates


  

    
remote-exec
Runs commands on the newly created resource over SSH/WinRM — e.g. installing an agent right after boot.

    
local-exec
Runs commands on the machine running Terraform — e.g. calling a webhook, writing a local file, triggering another pipeline.

  


  

    

      
      
Click above to SSH into the newly created instance and run a bootstrap script.

    

  


  
⚠
Common Trap
Provisioners run outside Terraform's normal state-tracked model — if a remote-exec script fails, the resource is still marked "tainted" but the failure isn't part of the declarative plan/apply diff the way a resource attribute change is.

  
🎯
Exam Tip
HashiCorp's own docs call provisioners a "last resort" — prefer cloud-init / instance user_data, or a dedicated configuration management tool like Ansible, wherever possible.
