01Foundations

Cloud Computing Foundations

Before OCI makes sense, you need to feel the pain it solves. Start in the data center your workload used to live in.

The traditional data center problem

Before cloud, every workload meant owning physical infrastructure: racks, servers, storage arrays, switches, and cooling — all sized for peak demand that might occur a few days a year.

Capital

💰 Procurement

Hardware ordered months in advance, paid upfront regardless of usage.

Facilities

⚡ Power & Cooling

Racks draw constant power; cooling systems run 24/7 to prevent thermal failure.

Elasticity

📈 Scaling

Scaling up means buying more gear; scaling down means idle, wasted capacity.

Risk

🛠 Downtime & Maintenance

Every patch, failed disk, or firmware upgrade is your team's responsibility, on your clock.

Hover a rack unit — this is what "capacity you must own" looks like at scale.

What cloud computing actually changes

Cloud computing replaces ownership with on-demand access to a shared, elastic pool of compute, storage, and networking — metered like a utility.

⚙️ On-Demand Self-Service

Provision compute or storage in minutes, no procurement cycle, no human approval chain.

🔄 Elasticity

Scale out during traffic spikes, scale in when demand drops — pay only for what's running.

📊 Measured Service

Usage is metered per second/hour; billing is transparent and usage-based.

🗂 Resource Pooling

Multiple tenants share physical hardware via virtualization, multiplexing idle capacity.

🛡 High Availability

Redundant power, network, and hardware across fault domains reduce single points of failure.

🌍 Global Reach

Deploy close to users across regions worldwide without building a single new building.

🎓
Exam TipNIST defines 5 essential characteristics of cloud computing: on-demand self-service, broad network access, resource pooling, rapid elasticity, and measured service. Oracle certification exams quote this list almost verbatim.
⚠️
Common Trap"Elasticity" and "scalability" are often used interchangeably in casual speech, but on the exam: scalability is the system's capacity to grow, while elasticity is the automatic, on-demand expansion and contraction of that capacity.
02Foundations

Virtualization

The technology that makes resource pooling possible: one physical machine, many isolated virtual ones.

A hypervisor sits between physical hardware and virtual machines, partitioning CPU, RAM, storage, and network into isolated slices. Type 1 (bare-metal) hypervisors run directly on hardware (used in OCI's compute fleet); Type 2 (hosted) hypervisors run atop a host OS (VirtualBox, VMware Workstation).

🖥 Type 1 — Bare Metal

Runs directly on hardware. Lower overhead, used in production data centers and clouds (e.g. OCI, Hyper-V, ESXi).

💻 Type 2 — Hosted

Runs on top of a host operating system. Simpler to set up, common for local development and testing.

  • CPU scheduling — the hypervisor time-slices physical cores across guest VMs.
  • Memory isolation — each VM gets a walled-off address space; one VM cannot read another's RAM.
  • Storage virtualization — physical disks are abstracted into virtual block volumes.
  • Network virtualization — virtual NICs and switches replicate physical networking in software.
  • Live migration — a running VM can move between physical hosts with near-zero downtime.

Which one should you choose?

Choose IaaS if…

Choose PaaS if…

04Foundations

Deployment Models

Same cloud technology, different questions about who owns the hardware and who else shares it.

Public

☁️ Public Cloud

Advantage: No capex, elastic, fastest to start.
Disadvantage: Less control over underlying hardware.
Use when: Variable workloads, new digital products.

Private

🏢 Private Cloud

Advantage: Full control, dedicated hardware.
Disadvantage: You bear capex again.
Use when: Strict regulatory or data-sovereignty needs.

Hybrid

🔗 Hybrid Cloud

Advantage: Keep sensitive workloads on-prem, burst to public cloud.
Disadvantage: Networking & identity complexity.
Use when: Gradual cloud migration.

Community

🤝 Community Cloud

Advantage: Shared cost among organizations with common requirements.
Disadvantage: Governance requires consensus.
Use when: Consortiums (e.g. government agencies, research groups).

Multi-cloud

🧩 Multi-Cloud

Advantage: Avoid vendor lock-in, best-of-breed services.
Disadvantage: Operational overhead, multiple skillsets.
Use when: Risk diversification is a business priority.

07OCI Architecture

OCI Overview: Regions & Realms

OCI's physical footprint, from largest to smallest: Realm → Region → Availability Domain → Fault Domain → Data Center.

🌐 Realm

A set of regions isolated from other realms for compliance (e.g. OC1 commercial, OC2 government).

📍 Region

A localized geographic area (e.g. US East, UK South) containing one or more Availability Domains.

🏢 Availability Domain

One or more data centers within a region, isolated from failures in other ADs.

🗄 Fault Domain

A grouping of hardware within an AD, isolating power/hardware failures at rack level.

Explore the global backbone

Click a region marker to see its details. OCI connects regions via Oracle's own private global backbone rather than the public internet.

Click a region to view realm, ADs, and typical use case.

🎓
Exam TipNot every region has 3 Availability Domains — many smaller regions have only 1 AD but always have 3 Fault Domains, so multi-AD HA design isn't possible everywhere. Always check fault-domain-only design for single-AD regions.

12Governance

Tenancy & Compartments

Your entire OCI footprint lives inside one Tenancy — a logical container for every resource you own. Compartments subdivide it for isolation and governance.

Click nodes to expand or collapse. This mirrors the structure you'll build for a real organization: separating environments, teams, or cost centers.

  • 🏛 Tenancy (root compartment)
    • 📁 Dev
      • 📦 Compute, VCN, Block Volumes
    • 📁 QA
      • 📦 Test databases, staging LB
    • 📁 Production
      • 📁 Finance
        • 📦 ERP workloads
      • 📁 HR
        • 📦 HCM workloads
🎓
Exam TipThe root compartment is the Tenancy itself. Policies attached at a parent compartment are inherited by all child compartments — a policy on Production applies to Finance and HR beneath it, unless explicitly scoped narrower.

Compartment design principles

  • Design around organizational structure (teams) or lifecycle (dev/test/prod) — pick one dominant axis and stay consistent.
  • Keep networking (VCNs) in a dedicated compartment if multiple teams share the same network.
  • Avoid deep nesting beyond 3–4 levels; it complicates policy management more than it helps.

Tagging & Naming Conventions

Tags make cost tracking and governance queryable instead of guesswork.

🏷 Freeform Tags

Simple key-value pairs, no validation, applied ad hoc. Good for quick labeling, prone to typos and inconsistency at scale.

📐 Defined Tags

Organized into tag namespaces with controlled values, enforced permissions on who can apply them. Used for cost tracking, automation, and compliance.

Cost Tracking Tag Example

CostCenter.Department = "Finance"
CostCenter.Project = "Q3-Migration"

Governance Tag Example

Environment.Type = "Production"
Compliance.DataResidency = "IN"

15Identity & Access

Identity & Access Management

IAM answers three questions for every request: who are you, what are you allowed to do, and what did you actually do.

🔑 Authentication

Proving identity — username/password, API key, federated login.

🛂 Authorization

Determining what an authenticated identity is permitted to do, via policies.

📋 Accounting

Recording what happened — Audit logs capture every API call for compliance and forensics.

Identity Domains

Isolated, self-contained user/group populations within a tenancy — think "an IAM realm within your realm."

RBAC

Role-Based Access Control — permissions attached to roles/groups, not individual users.

Principals

Anything that can be authenticated: a user, an instance principal, or a resource principal.

Dynamic Groups

Groups whose membership is defined by matching rules (e.g. all instances in a compartment) rather than static user lists — lets compute instances themselves hold permissions.

Tokens & Sessions

Short-lived credentials issued after authentication, used to authorize subsequent API calls without re-sending a password.

Federation

Trusting an external identity provider (Azure AD, Google Workspace) instead of managing separate local credentials.

18Identity & Access

Federation & Single Sign-On

Instead of maintaining a second set of passwords, OCI trusts an external Identity Provider.

Common Identity Providers

Microsoft Entra ID (Azure AD), Google Workspace, on-prem Active Directory via ADFS, or any SAML/OIDC-compliant IdP.

Protocols

SAML 2.0 — XML-based assertions, common in enterprise SSO.
OIDC — JSON/OAuth2-based, common in modern web & mobile apps.

1. Request

User hits an OCI resource, gets redirected to IdP.

2. Authenticate

User logs in once at the IdP (Entra ID / Google).

3. Assertion

IdP issues a signed SAML/OIDC token back to OCI.

4. Access Granted

OCI trusts the assertion and maps the user to local groups.

19Identity & Access

Policies & Verbs

OCI policies read almost like English sentences. Master this syntax and the certification's policy questions become easy points.

Allow group Developers to manage instances in compartment Production

Every policy statement follows: Allow <subject> to <verb> <resource-type> in <location> [where <condition>].

Try the policy editor

Write a policy statement and validate its syntax.

Policy verbs, from weakest to strongest

inspect

List resources & metadata only. No details, no read.

read

Inspect + get user-specified metadata and the resource itself.

use

Read + act on existing resources, but cannot create or delete.

manage

Full control: create, update, delete, and everything below it.

Click a verb above to see exactly what it unlocks.

⚠️
Common TrapEach verb is a strict superset of the ones before it: manage ⊃ use ⊃ read ⊃ inspect. Granting "manage" when a team only needs "use" is a classic over-privilege mistake the exam will probe.

23Wrap-Up

Exam Cheat Sheet

The condensed version of everything above — skim this the night before the exam.

Key Definitions

  • Elasticity: automatic scale up/down
  • Fault Domain: rack-level isolation within an AD
  • Availability Domain: DC-level isolation within a region
  • Dynamic Group: rule-based, not static membership
  • Compartment: logical resource isolation boundary

Important Policy Verbs

  • inspect → list only
  • read → inspect + get
  • use → read + act (no create/delete)
  • manage → full lifecycle control

Important CLI Commands

oci iam user list
oci iam group list
oci iam compartment create
oci iam policy list
oci iam region list

Important Policy Template

Allow group <G> to <verb> <resource> in compartment <C>
