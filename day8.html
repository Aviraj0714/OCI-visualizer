01Methodology

Troubleshooting Methodology

Six repeatable steps that separate structured diagnosis from guessing.

1. Identify

What is actually broken, and for whom?

2. Isolate

Narrow down which layer/component is responsible.

3. Diagnose

Determine the specific root cause within that layer.

4. Resolve

Apply the fix.

5. Validate

Confirm the fix actually resolved the issue for the user.

6. Prevent

Address the underlying cause so it doesn't recur.

03Methodology

Root Cause Analysis

The "5 Whys" technique: keep asking "why" until you reach the actual root cause, not just a symptom.

Problem: Checkout API returned 502 errors for 30% of requests.

Fishbone (Ishikawa) Diagram

Groups potential causes into categories (People, Process, Technology, Environment) to explore breadth before depth.

Fault Tree Analysis

Works backward from the failure, mapping all combinations of conditions that could produce it — used for complex, multi-cause outages.

Listener

Defines the protocol/port the LB accepts traffic on (e.g. HTTPS:443).

Health Check

29Certification Center

Cheat Sheets

Compute & SSH

  • No SSH? Check: key, user, NSG, Security List, route, public IP, cloud-init
  • Serial Console works even with zero network connectivity
  • Run Commands execute without needing SSH at all

Network

  • Diagnose bottom-up through OSI layers
  • 2 tunnels per IPSec connection for redundancy
  • FastConnect = dedicated private link, bypasses the internet

Load Balancer

  • 502 = bad response from backend; 503 = no healthy backend; 504 = backend too slow
  • Unhealthy backend ≠ application down — check firewall/port/path first

Storage & Incident Response

  • NFS mount timeout → check mount target NSG/Security List first
  • 5 Whys: keep asking until you hit the real root cause, not a symptom
  • Always Validate + Prevent, not just Resolve
